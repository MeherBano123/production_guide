Rate Limiting

Part 1 · Traffic and platform

Fig. 1 The limiter lets normal clients through and throttles only the one that exceeds its budget.

What is it?

Rate limiting caps how many requests a client (user, API key or IP) may make within a time window, for example 100 per minute. Requests over the cap are rejected, usually with HTTP 429 Too Many Requests, or queued. Common algorithms: fixed window, sliding window, token bucket, leaky bucket.

P14
Part 1 · Traffic and platform

When is it used?

On every public or partner API, on login and password-reset endpoints, on expensive endpoints (search, exports, LLM calls), and between internal services so one noisy caller cannot starve the others.

What problem does it solve?

One buggy client loop, a scraper or a credential-stuffing bot can saturate your CPU, database connections or paid third-party quota and take the service down for everyone. Rate limiting enforces fairness and protects your bill.

In production

A SaaS company ships a mobile app with a bug that retries a sync call in a tight loop. Within minutes one customer’s phones send 40,000 requests per minute and the Postgres connection pool is exhausted for all tenants. Afterwards the team adds a token-bucket limiter at the gateway (60 requests/min per API key, burst of 20), backed by Redis counters, returning 429 with a Retry-After header. The next misbehaving client gets throttled; everyone else sees no change.

Caching

Part 1 · Traffic and platform

Fig. 2 Hits are answered from memory. Only misses reach the database, and they refill the cache on the way back.

What is it?

Caching stores the result of expensive work (a database query, a rendered page, an API response) in a faster place, usually memory, so the next request can reuse it. Layers: browser, CDN, application memory, shared cache (Redis, Memcached), database buffer cache.

P16
Part 1 · Traffic and platform

When is it used?

For read-heavy data that changes rarely or can be slightly stale: product catalogs, user profiles, configuration, rendered fragments, expensive aggregates, sessions.

What problem does it solve?

Cuts latency from tens of milliseconds to sub-millisecond and removes load from the database, which is the hardest component to scale.

In production

An e-commerce homepage runs 14 queries to build its “top categories” and “trending” blocks, 3,000 times per second on sale day. Database CPU sits at 90%. The team caches the rendered blocks in Redis with a 60-second TTL. DB load drops about 85% and p95 page time falls from 900 ms to 120 ms. The cost: a price change can take up to a minute to appear on the homepage, a trade-off the business accepts.

Load Balancing

Part 1 · Traffic and platform

Fig. 3 Health checks pull the dead server out of rotation; the other two absorb its traffic.

What is it?

A load balancer distributes incoming traffic across multiple instances of a service using a policy such as round robin, least connections or consistent hashing. It works at layer 4 (TCP) or layer 7 (HTTP, can route by path or header) and runs health checks to stop sending traffic to dead instances.

P18
Part 1 · Traffic and platform

When is it used?

Any time more than one instance serves the same traffic: web tiers, API fleets, internal microservices, database read paths.

What problem does it solve?

Removes the single server as both a capacity limit and a single point of failure, and lets you deploy, scale and replace instances without downtime.

In production

A ticketing site runs four API servers. One crashes at 8 pm during a presale. The application load balancer health-checks /healthz every 5 seconds and pulls the dead node after two failures; the other three absorb the traffic and users see a few failed requests instead of an outage. Later the team switches from round robin to least-outstanding-requests because a few slow endpoints were piling work onto unlucky nodes.

Reverse Proxies

Part 1 · Traffic and platform

Fig. 4 The proxy faces the internet so app servers never handle TLS, slow clients or raw exposure.

What is it?

A reverse proxy sits in front of your servers and forwards client requests to them, so clients only ever talk to the proxy (Nginx, HAProxy, Envoy, Caddy, Traefik). It can terminate TLS, compress, cache, rewrite URLs, buffer slow clients and add headers.

P20
Part 1 · Traffic and platform

When is it used?

In front of nearly every production web app: to hide internal topology, serve static files, terminate HTTPS, route /api to one service and / to another, and absorb slow-client connections.

What problem does it solve?

Application servers (Uvicorn, Gunicorn, Node) are poor at TLS, slow uploads and raw internet exposure. The proxy handles those and gives you one place for routing, security headers and access logs.

In production

A FastAPI service exposed directly on port 8000 stalls whenever mobile users on poor networks upload 20 MB files slowly, because each upload holds a worker. Putting Nginx in front with request buffering means Nginx receives the whole upload and hands it to the app in one fast burst. Workers stay free, and the same Nginx now terminates TLS and serves /static directly.

API Gateways

Part 1 · Traffic and platform

Fig. 5 One front door for auth, throttling and routing, instead of re-implementing them in every service.

What is it?

An API gateway is a single entry point for client traffic to many backend services. It handles cross-cutting concerns: authentication, rate limiting, routing, protocol translation, response aggregation, quotas and analytics. Examples: Kong, AWS API Gateway, Apigee, Envoy-based gateways.

P22
Part 1 · Traffic and platform

When is it used?

Microservice architectures, public or partner APIs, mobile backends that call several services, and anywhere you need per-client keys and usage plans.

What problem does it solve?

Without a gateway every service re-implements auth, throttling and logging inconsistently, and clients must know the address and protocol of every service.

In production

A fintech has 12 services. Each team implemented JWT validation slightly differently and one forgot to check token expiry. They put a gateway in front: it validates JWTs once, applies per-plan rate limits, routes /payments and /accounts to different services and stamps a request ID on everything. A security fix becomes one gateway config change instead of 12 pull requests.

CI/CD

Part 1 · Traffic and platform

Fig. 6 Every change passes the same automated gates on its way to production.

What is it?

Continuous Integration builds and tests every change automatically when it is pushed. Continuous Delivery packages passing builds so they are always releasable; Continuous Deployment releases them to production automatically. Tools: GitHub Actions, GitLab CI, Jenkins, CircleCI.

P24
Part 1 · Traffic and platform

When is it used?

On every repository from day one: pull requests run lint, tests and security scans; merges to main build artifacts and deploy to staging, then production.

What problem does it solve?

Eliminates “works on my machine”, manual error-prone deploy steps and big-bang releases. Small, frequent, automated releases are less risky and easier to roll back.

In production

A team deploys by SSH-ing into a server and running git pull on Fridays. One Friday a missing migration plus an untested change takes checkout down for two hours. They adopt GitHub Actions: tests and linters on each PR; on merge, build a Docker image, deploy to staging, run smoke tests, promote to production. Deploys go from a stressful weekly ritual to ten uneventful ones a day.

Docker

Part 1 · Traffic and platform

Fig. 7 An image is a stack of layers. The same image runs identically on a laptop, in CI and in production.

What is it?

Docker packages an application with its runtime, libraries and configuration into an image; a running instance of an image is a container. Containers share the host kernel, so they are far lighter than virtual machines, yet isolated through namespaces and cgroups.

P26
Part 1 · Traffic and platform

When is it used?

Packaging services for deployment, reproducible local environments (Docker Compose), CI build and test jobs, running different dependency versions side by side.

What problem does it solve?

Differences in OS, language versions and system libraries between laptop, CI and production. The same image runs everywhere.

In production

A model service needs Python 3.10, a specific CUDA library and a system package. The laptop, CI runner and production VM each differ, and a deploy fails with an obscure libssl error. The team writes a Dockerfile pinning the base image and dependencies. The identical image is tested in CI and run in production, and onboarding a new engineer drops from a day to docker compose up.

Kubernetes

Part 1 · Traffic and platform

Fig. 8 When a node dies, the control plane sees the gap between desired and actual state and reschedules the pods.

What is it?

Kubernetes (K8s) is a container orchestrator. You declare the desired state (5 replicas of this image with these resources) and the control plane continuously schedules containers onto nodes, restarts failures, scales, rolls out updates and wires networking and storage. Core objects: Pod, Deployment, Service, Ingress, ConfigMap, Secret.

P28
Part 1 · Traffic and platform

When is it used?

When you run many containers or services across multiple machines and need self-healing, rolling updates, autoscaling and service discovery. Often overkill for a handful of services on one or two VMs.

What problem does it solve?

Manually deciding which machine runs which container, restarting crashed ones and updating without downtime does not scale beyond a few services.

In production

A company with 40 services on hand-managed VMs loses a node at 3 am and nobody notices for an hour because the services pinned to it are down. On Kubernetes, the scheduler reschedules the affected pods onto healthy nodes within about a minute, readiness probes keep traffic away until they are ready, and a Horizontal Pod Autoscaler grows busy services at the morning peak. The price is operational complexity, which is why a three-service startup is often better on a managed container platform.

Service Discovery

Part 1 · Traffic and platform

Fig. 9 Callers ask for a name, not an IP, so pods can come and go freely.

What is it?

Service discovery is how services find each other’s network addresses dynamically instead of using hard-coded IPs. Client-side: the caller queries a registry (Consul, Eureka). Server-side: DNS or a load balancer resolves it (Kubernetes Services and CoreDNS).

P30
Part 1 · Traffic and platform

When is it used?

Whenever instances come and go: autoscaling, deploys, container restarts. Any container or microservice environment.

What problem does it solve?

IP addresses change constantly in dynamic environments; hard-coded addresses break on every redeploy or scale event.

In production

The orders service calls inventory at 10.0.3.17. After an autoscale event and a deploy, the inventory pods get new IPs and orders starts failing with “connection refused”. With Kubernetes, orders calls http://inventory.shop.svc.cluster.local. The Service tracks healthy pod IPs and DNS gives a stable name, so scaling inventory from 3 to 30 pods needs no change in the caller.

Circuit Breakers

Part 2 · Resilience patterns

Fig. 10 After enough failures the breaker opens and stops calling the dependency. Trial calls decide when to close it again.

What is it?

A circuit breaker wraps calls to a dependency and counts failures. When failures cross a threshold it “opens” and fails calls immediately without trying. After a cool-down it goes “half-open”, lets a few trial requests through, and closes again if they succeed.

P34
Part 2 · Resilience patterns

When is it used?

Around calls to remote services, third-party APIs and databases, where a slow or failing dependency could drag the caller down.

What problem does it solve?

Prevents cascading failure: callers piling up threads waiting on a dead dependency, exhausting their own resources and failing too. It also gives the struggling dependency room to recover instead of hammering it.

In production

A checkout service calls a recommendation service for “you may also like”. Recommendations starts taking 30 seconds per call, checkout threads fill up waiting, and now checkout itself is down. With a circuit breaker (open after 50% failures over 20 calls), checkout skips recommendations once the breaker trips, renders the page without them and probes every 30 seconds. The revenue-critical flow survives a non-critical dependency failing.

11

Timeouts

Part 2 · Resilience patterns

Fig. 11 A timeout turns an unbounded wait into a bounded, handled error.

What is it?

A timeout is the maximum time you will wait for an operation (connect, read, query, whole request) before giving up. Good systems set them at every boundary, plus an overall deadline that propagates downstream.

P36
Part 2 · Resilience patterns

When is it used?

On every network call and blocking operation. Many libraries default to no timeout or a very long one, so you must set them explicitly.

What problem does it solve?

Without timeouts, a hung dependency holds threads, connections and memory indefinitely, turning a slow failure into a full outage.

In production

A Python service calls a payment provider with requests.post() and no timeout. The provider has a partial outage where connections open but never respond. Each stuck call holds a worker, within minutes all 32 workers are blocked, even /health hangs and the pods get killed. The fix: connect timeout 2 s, read timeout 5 s, and an overall per-request deadline, so failure shows up as fast, handled errors.

Retries

Part 2 · Resilience patterns

Fig. 12 Retry only errors that are likely to be transient, and only a bounded number of times.

What is it?

Retrying means automatically repeating a failed operation on the assumption that the failure is transient (a network blip, brief overload, a 503). Good retry logic only retries errors that are safe and likely to succeed, limits attempts, and uses backoff with jitter.

P38
Part 2 · Resilience patterns

When is it used?

Calls to remote services, queue consumers, database deadlock errors, and anything exposed to transient faults.

What problem does it solve?

Transient failures are normal in distributed systems, and without retries they become user-visible errors. But naive retries amplify outages (retry storms).

In production

A dependency resets about 1% of connections and users see random errors. Adding up to 3 retries on connect errors and 503s fixes it, until the dependency has a real outage and every client retries 3 times, tripling load when it is weakest. The team adds a retry budget (retries capped at 10% of traffic), stops retrying 4xx responses and puts retries behind a circuit breaker.

Exponential Backoff

Part 2 · Resilience patterns

Fig. 13 Each wait doubles, up to a cap. Random jitter on top stops thousands of clients retrying in the same instant.

What is it?

Exponential backoff increases the wait between retries multiplicatively (1 s, 2 s, 4 s, 8 s…) up to a cap, and adds random jitter so clients do not all retry at the same instant.

P40
Part 2 · Resilience patterns

When is it used?

In every retry loop against a shared resource: APIs, databases, queues, cloud SDKs (most build it in).

What problem does it solve?

Fixed-interval retries from many clients synchronize into waves (a thundering herd) that stop a recovering service from recovering. Backoff reduces the load and jitter spreads it out.

In production

A cache cluster restarts and 2,000 app instances all retry every second. Each wave of 2,000 reconnects overwhelms the cache again, so it stays down for 20 minutes. After switching to exponential backoff (base 200 ms, cap 30 s) with full jitter, retries spread over time, the cache warms gradually and recovery takes about 2 minutes.

Idempotency

Part 2 · Resilience patterns

Fig. 14 The server remembers each key, so a retried request returns the original result instead of charging again.

What is it?

An operation is idempotent if doing it several times has the same effect as doing it once. HTTP GET, PUT and DELETE are idempotent by definition; POST is not, so APIs add idempotency keys: the client sends a unique key, the server stores the result and returns it for duplicates.

P42
Part 2 · Resilience patterns

When is it used?

Payments, order creation, sending emails, any write that clients or queues may retry. Essential with at-least-once message delivery.

What problem does it solve?

Retries, double-clicks, network timeouts (where the client cannot know whether the request succeeded) and redelivered messages cause duplicate charges, orders and emails.

In production

A customer taps “Pay” on a poor connection, the request times out, the app retries, and the customer is charged twice. The team adds an Idempotency-Key header (a UUID per checkout attempt). The server stores key to response in a table with a unique constraint; the retry returns the stored result without charging again.

Message Queues

Part 3 · Messaging and real-time

Fig. 15 The request returns immediately; workers drain the queue at their own pace and survive restarts.

What is it?

A message queue is a buffer where producers put messages (jobs) and consumers take them off and process them asynchronously. Messages persist until acknowledged. Examples: RabbitMQ, Amazon SQS, Redis-backed queues (Celery, BullMQ), Kafka (log-based).

P46
Part 3 · Messaging and real-time

When is it used?

Slow or unreliable work you do not want in the request path: emails, image or video processing, PDF generation, ML inference, webhooks, imports. Also smoothing traffic spikes.

What problem does it solve?

Decouples producers from consumers. Requests return quickly, spikes are absorbed by the queue, workers scale independently, and work survives a consumer crash.

In production

A signup endpoint sends a welcome email, generates a PDF and calls a CRM synchronously. It takes 6 seconds and fails whenever the email provider is down. The endpoint now saves the user, publishes three messages and returns in 80 ms. Workers handle them, and when the email provider is down the messages wait and retry instead of failing the signup.

16

Pub/Sub

Part 3 · Messaging and real-time

Fig. 16 Every subscriber gets its own copy. New subscribers need no change to the publisher.

What is it?

Publish/subscribe is a messaging pattern where publishers send messages to a topic without knowing who receives them, and every subscriber gets its own copy. Examples: Google Pub/Sub, SNS, Kafka topics with consumer groups, RabbitMQ fanout exchanges.

P48
Part 3 · Messaging and real-time

When is it used?

When one event must trigger several independent reactions: “order placed” leads to email, inventory, analytics and fraud checks.

What problem does it solve?

The publisher no longer has to know about, call and wait for each consumer, and new consumers can be added without changing the publisher.

In production

When an order is placed, the orders service used to call four services directly, and adding a loyalty-points service required a change and deploy of orders. Now orders publishes order.placed once; billing, inventory, email and analytics each subscribe independently. Loyalty was added later by another team without touching orders code.

Event-Driven Architecture

Part 3 · Messaging and real-time

Fig. 17 Services announce facts and whoever cares reacts. A slow consumer delays only its own work.

What is it?

In event-driven architecture, services communicate by emitting and reacting to events (facts such as InvoicePaid) through a broker instead of calling each other synchronously. Variants: event notification, event-carried state transfer, event sourcing.

P50
Part 3 · Messaging and real-time

When is it used?

Complex workflows with many reactors, loosely coupled teams, audit-heavy domains, near-real-time data pipelines.

What problem does it solve?

Tight coupling and synchronous call chains, where one slow service blocks everything and every new feature touches many services.

In production

A logistics platform chains shipping, billing, notifications and analytics with synchronous REST calls, so a billing outage blocks shipments. They move to events: ShipmentDispatched is published and billing and notifications consume it at their own pace. A billing outage now only delays invoices. The cost: answering “why didn’t X happen?” means tracing events across services, so they invest in correlation IDs and distributed tracing.

Distributed Transactions

Part 3 · Messaging and real-time

Fig. 18 Without a coordinated rollback, a failure in step 3 leaves steps 1 and 2 dangling.

What is it?

A distributed transaction is a business operation that must update data in several independent databases or services atomically: all succeed or all fail. The classic approach is two-phase commit (2PC) with a coordinator. In microservices it is usually avoided in favor of sagas.

P52
Part 3 · Messaging and real-time

When is it used?

Money movement, order plus inventory plus payment, any multi-service write where partial completion would be wrong.

What problem does it solve?

A crash between step 1 and step 2 leaves data inconsistent: money taken but no order, or stock reserved but never released. Yet 2PC is slow, blocks on failures and is unsupported by many stores and external APIs.

In production

A travel booking must reserve a flight, reserve a hotel and charge a card, each in a different system. The flight and hotel are reserved, the card charge fails, and customers see held seats for nothing. 2PC across three vendors is impossible because external APIs do not support it, so the team models the flow as a saga with compensations: if payment fails, release the hotel and the flight.

Saga Pattern

Part 3 · Messaging and real-time

Fig. 19 If a step fails, compensating actions undo the earlier steps in reverse order.

What is it?

A saga splits a distributed transaction into a sequence of local transactions, each with a compensating action that undoes it if a later step fails. Two styles: choreography (services react to each other’s events) and orchestration (a central coordinator drives the steps).

P54
Part 3 · Messaging and real-time

When is it used?

Multi-service workflows with long-running or external steps: order fulfilment, bookings, onboarding, refunds.

What problem does it solve?

Gives eventual all-or-nothing behavior without a global lock or 2PC.

In production

Order saga: (1) create order PENDING, (2) reserve stock, (3) charge card, (4) schedule shipping. The charge fails at step 3, so the orchestrator runs compensations: release stock and mark the order CANCELLED. If the orchestrator crashes mid-saga it resumes from persisted state. Compensations must be idempotent, and some actions (an email already sent) cannot be undone, so design for that up front.

Dead Letter Queues

Part 3 · Messaging and real-time

Fig. 20 Poison messages are parked for inspection instead of blocking the queue or being lost.

What is it?

A dead letter queue (DLQ) is a holding queue where messages go after failing processing too many times, or after expiring or being rejected. They are kept for inspection and replay instead of being dropped or retried forever.

P56
Part 3 · Messaging and real-time

When is it used?

With any queue consumer: SQS redrive policies, RabbitMQ dead-letter exchanges, Kafka dead-letter topics.

What problem does it solve?

“Poison messages” (malformed, or triggering a bug) otherwise block the queue or loop forever burning CPU, and discarding them silently loses data.

In production

One malformed payment webhook crashes the consumer on every attempt. The queue redelivers it endlessly, the consumer restarts continually and messages behind it are delayed. With maxReceiveCount=5 and a DLQ, the message moves aside after five failures and the queue flows again. An alert fires when DLQ depth is above zero, an engineer fixes the parser and replays the message.

Cron Jobs

Part 3 · Messaging and real-time

Fig. 21 A job that runs once, safely, and loudly reports when it does not.

What is it?

Cron jobs are tasks scheduled to run at set times or intervals (0 2 * * * means 2 am daily). Implemented by OS cron, Kubernetes CronJobs, Celery beat, cloud schedulers.

P58
Part 3 · Messaging and real-time

When is it used?

Nightly reports, cleanup of expired data, billing runs, cache warming, data sync, backups.

What problem does it solve?

Automates recurring work so nobody has to remember. The production traps: overlapping runs, double execution on several instances, silent failures, time zones and daylight saving.

In production

A nightly invoice job runs on each of three app servers, so customers receive triple invoices. The fix: a single scheduler (or a distributed lock), an idempotent job with a unique invoice-per-period constraint, no-overlap protection, UTC schedules, and a dead-man’s-switch alert if the job does not report success by its deadline.

WebSockets

Part 3 · Messaging and real-time

Fig. 22 One persistent connection; either side can send at any moment.

What is it?

WebSocket is a protocol giving a persistent, full-duplex connection between client and server over one TCP connection (started with an HTTP upgrade). Either side can send messages at any time with little overhead.

P60
Part 3 · Messaging and real-time

When is it used?

Chat, live dashboards, collaborative editing, multiplayer games, trading tickers, live notifications.

What problem does it solve?

HTTP request/response polling is wasteful and laggy for real-time updates.

In production

What is it?

In production

A transfer from account A to B locks A then B, while a concurrent transfer from B to A locks B then A. The database reports deadlock detected and kills one. The fix: always lock in a consistent order (lower account ID first), keep transactions short, and retry on deadlock errors.

Part 7 · Releases and deploys

Fig. 55 Code rolls back easily. Data does not, so keep every migration compatible with the previous version.

What is it?

P134

When is it used?

When a release causes errors, latency or wrong behavior, and rolling back is faster than fixing forward.

What is it?

Part 7 · Releases and deploys

When is it used?

Every service behind a load balancer or orchestrator.

What problem does it solve?

Without them, traffic keeps going to dead or broken instances.

A health endpoint always returns 200. One instance’s DB connection pool is exhausted, it still answers /health but fails every real request, and the load balancer keeps sending it traffic. Part 7 · Releases and deploys

Fig. 57 Readiness decides who gets traffic; liveness decides who gets restarted. Keep them different.

What is it?

Kubernetes probes. Liveness asks “is this process stuck? If so, restart it.” Readiness asks “can it accept traffic right now? If not, remove it from Service endpoints.” Startup probes give slow-booting apps time before liveness begins.

P138
Part 7 · Releases and deploys

When is it used?

All Kubernetes workloads.

In production

A service loads a 2 GB ML model at startup (60 seconds). With no readiness probe, every deploy sends traffic to pods that return errors for a minute. What is it?

TCP is connection-oriented, reliable and ordered: handshake, acknowledgements, retransmission, congestion and flow control. UDP is connectionless with no delivery or ordering guarantees and minimal overhead: fire-and-forget datagrams.

In production

A multiplayer game sends player positions over TCP. One lost packet stalls everything behind it until retransmitted, causing stutter. Raw YAML copy-pasted per environment drifts and is error-prone. Helm templates once, configures per environment and versions the release.

In production

A team keeps three folders of near-identical YAML for dev, staging and prod, and a fix applied in prod is forgotten in staging. They move to one Helm chart with values-dev.yaml and values-prod.yaml, and CI runs helm upgrade --install --atomic. A bad release is reverted with helm rollback app 12. Caveats: templates can become unreadable, so run helm template and lint in CI; Kustomize is an alternative.

Build Caching

What is it?

Build caching reuses the outputs of earlier build steps when their inputs have not changed: Docker layer cache, dependency caches (npm, pip, Maven), compiler caches (ccache), remote caches (Bazel, Gradle, Turborepo, Nx), CI cache actions.

P248
Part 12 · Versioning, infra and ops

When is it used?

CI pipelines, monorepos, container builds.

What problem does it solve?

Rebuilding everything from scratch on every commit wastes minutes to hours, slowing feedback and costing money.

In production

A pipeline takes 22 minutes because each run reinstalls dependencies and rebuilds every package in a monorepo. The team orders the Dockerfile so COPY package.json and npm ci come before copying source (so that layer is cached), adds a CI cache for the package store and uses a remote build cache for unchanged packages: 22 minutes drops to 5. The danger: stale or poisoned caches giving non-reproducible results, so key caches on the lockfile hash.

Dependency Hell

Part 12 · Versioning, infra and ops

Fig. 108 Two dependencies demand incompatible versions of a third, so no single version satisfies both.

What is it?

Dependency hell is when dependency constraints conflict or become unmanageable: diamond dependencies needing incompatible versions of one library, transitive upgrades breaking things, abandoned packages, deep trees, vulnerable versions you cannot upgrade.

P250
Part 12 · Versioning, infra and ops

When is it used?

It occurs in every ecosystem (npm, pip, Maven) and is managed with lockfiles, pinned versions, few dependencies, automated update bots and SBOMs.

What problem does it solve?

Builds break unpredictably, security patches are blocked, and “works on my machine” returns.

In production

Service A needs libX >=2,<3 and service B needs libX <2, so upgrading one breaks the other, while a critical CVE in libX 1.x cannot be patched. On another day an unpinned transitive dependency releases a breaking change and Friday’s build fails with no code changes. Defenses: commit lockfiles, reproducible builds, Dependabot or Renovate with CI to upgrade often in small steps, fewer dependencies, and container images pinned by digest.

Production Incidents

Part 12 · Versioning, infra and ops

Fig. 109 Mitigate first, understand later. Roles and a process prevent chaos at 2 am.

What is it?

A production incident is an unplanned event that degrades or interrupts a service for users: an outage, data corruption, a security breach, a severe slowdown. It is handled with a defined process: detect, triage and set severity, assign an incident commander, communicate, mitigate, resolve, review.

P252
Part 12 · Versioning, infra and ops

When is it used?

Always. It is when, not if, so the process must exist before the incident.

What problem does it solve?

Without roles and process, incidents turn chaotic: everyone debugging the same thing, nobody communicating, fixes undone.

In production

At 02:10 the checkout error rate hits 30%. On-call acknowledges and declares SEV-1, and assigns an incident commander to coordinate, a communicator posting status-page updates every 30 minutes and an operations lead investigating. A recent deploy correlates, so they roll it back (mitigate first, find root cause later) and errors disappear at 02:34. Principle: restore service first, understand later.

On-Call

Part 12 · Versioning, infra and ops

Fig. 110 A clear escalation path, runbooks and sane alert volume keep on-call sustainable.

What is it?

On-call is a rota in which engineers take turns being reachable to respond to production alerts outside business hours, with primary and secondary responders, an escalation policy, runbooks and handoffs. Tools: PagerDuty, Opsgenie.

P254
Part 12 · Versioning, infra and ops

When is it used?

Any service with uptime expectations, and teams that own what they build (“you build it, you run it”).

What problem does it solve?

Ensures someone responds fast. Poorly run on-call burns people out and causes attrition.

In production

One senior engineer was the de facto 24/7 responder, got paged 15 times a night and quit. The new setup: 1-week rotations across 6 people, a secondary, alerts only for user-impacting issues with runbooks, time off after hard nights, a tracked pages-per-shift metric (target: under 2) and a rule that noisy alerts get fixed or deleted.

Postmortems

Part 12 · Versioning, infra and ops

Fig. 111 A blameless review that ends in tracked actions. Without actions it is only a story.

What is it?

A postmortem is a written review after an incident: timeline, impact, root causes and contributing factors, what went well and badly, and action items with owners and dates. Good ones are blameless: they focus on systems and process, not individuals.

P256
Part 12 · Versioning, infra and ops

When is it used?

After every significant incident and near miss, shared widely.

What problem does it solve?

Without postmortems the same incident repeats. With blame, people hide mistakes and learning stops.

In production

A postmortem for a 47-minute outage finds that a config change removed a database index, reviewers approved it because the diff looked trivial, and staging data was too small to reveal the slowness. Actions: (1) a CI check comparing query plans on production-sized data, (2) canary deploys for config changes, (3) an alert on query latency, (4) a runbook update, each with an owner and due date. Three months later a follow-up review shows 3 of 4 closed. A postmortem that produces no tracked actions is theatre.

SYNTHESIS

Six patterns that repeat

  1. Failure spreads along the path of least isolation.Timeouts, circuit breakers, bulkheads, backpressure and rate limits are the same idea at different layers: stop one slow or failing part from taking down the rest.
  2. Anything retried must be safe to repeat.Retries, backoff, idempotency, dead letter queues, webhooks and sagas only work together. Retries without idempotency create duplicate charges.
  3. State is what makes systems hard.Scaling, caching, locking, replication, sharding and consistency all come from state that has to live in more than one place.
  4. Every cache and every replica is a copy that can be wrong.Decide in advance how stale is acceptable, and who is allowed to see which copy.
  5. Changes need an exit.Feature flags, canaries, blue-green, rollbacks, expand/contract migrations and schema versioning exist so a bad change can be undone without heroics.
  6. You cannot fix what you cannot see, and you cannot trust what you never tested.Monitoring, tracing, SLOs, backups, failover and chaos engineering all end in the same question: did you actually try it?
